연동 자동화 가능성 조사

  • 작성일 2026-10-18
  • 대상: CS 질문 답변 PoC (cs-qa-mvp)
  • 근거: 카카오·노션 공식 문서, 실제 노션 보드와 PoC 코드 확인
전체 흐름은 공식 기능으로 자동화할 수 있습니다. 다만 카카오 쪽은 승인·인증·비용 조건이 붙습니다. 그리고 "언제 티켓을 만들 것인가"를 판단하는 대화 관리 기능은 PoC에 새로 만들어야 합니다. 노션 쪽은 카드 생성과 단계 변경 감지 모두 API로 할 수 있습니다. 하지만 이벤트가 늦게 오거나 빠질 수 있어 보정 장치가 필요합니다.
가능
  • 노션에 CS 카드 생성
  • 단계·우선순위·카테고리 기록
  • 할당일·완료일 자동 기록
  • 사용자 구분키로 문의자 식별
조건부
  • 채널 문의에 답변 전달 (5초 제한으로 콜백 필요)
  • 노션 단계 변경 감지 (공개 서버 필요)
  • 처리 결과 먼저 보내기 (인증·비용)
우리 쪽 개발
  • 대화 단위 관리 (지금은 질문 한 줄만 받음)
  • 티켓 생성 시점 판단
  • 카카오·노션 요청을 받는 공개 HTTPS 서버
API로 불가
  • 노션 카드 템플릿 새로 만들기
  • 노션 상태 그룹·선택지 이름 바꾸기
  • CS 번호·등록일시 직접 쓰기

1전체 흐름과 단계별 판정

STEP 1 채널로 문의 접수 조건부 채널에 연결한 챗봇이 메시지를 우리 서버로 넘김 카카오 챗봇 → 우리 서버
STEP 2 답변 생성·전달 조건부 5초 안에 못 끝나면 콜백으로 나중에 답변 PoC 파이프라인
STEP 3 노션 티켓 생성 가능 생성은 API로 가능. 생성 시점 판단은 새로 개발 우리 서버 → 노션
STEP 4 크루 처리·단계 감지 조건부 단계가 바뀌면 웹훅으로 알림. 지연·유실 대비 필요 운영 크루 · 노션 → 우리 서버
STEP 5 결과 통지 조건부 Event API 또는 알림톡. 각각 인증·비용 조건 있음 우리 서버 → 카카오

2단계별 상세

조건부

STEP 1. 채널로 문의 접수

되는 것

  • 채널에 카카오 챗봇을 연결하면 사용자 발화가 우리 서버(스킬 서버)로 전달됩니다.
  • 요청마다 사용자 구분키가 함께 옵니다. 같은 사람을 다시 알아볼 수 있어서, 대화 묶음이나 티켓의 기준값으로 쓸 수 있습니다.

조건 · 확인 안 된 것

  • 사용자 구분키는 봇마다 다르게 발급됩니다. 봇을 바꾸면 같은 사람도 다른 키를 받습니다.
  • 전화번호는 넘어오지 않습니다.
  • 챗봇을 채널에 연결·배포하는 절차와 심사 여부는 이번 조사에서 확인하지 않았습니다.

공식 문서 원문

"현재는 botUserKey만 제공합니다." / "동일한 사용자더라도, 봇이 다르면 다른 id가 발급됩니다."카카오 비즈니스 가이드 · 스킬 응답·요청 형식
"카카오톡 채널에서 제공하는 사용자 구분키(비식별) 입니다."같은 문서 · plusfriendUserKey 설명
조건부

STEP 2. 답변 생성·전달

되는 것

  • 카카오는 스킬 서버의 응답을 5초 기다립니다. PoC는 LLM을 여러 번 호출하므로 이 안에 끝나지 않을 수 있습니다.
  • 콜백을 쓰면 먼저 "확인 중" 응답을 보내고, 답변이 준비되면 받은 주소로 다시 보낼 수 있습니다.

조건 · 확인 안 된 것

  • 콜백 주소의 유효시간이 문서마다 1분 또는 5분으로 다릅니다. 어느 쪽이든 PoC 처리 시간보다는 깁니다.
  • 콜백에 사전 신청·승인이 필요한지는 공식 문서에 없습니다. 개발자 포럼에 관리 메뉴의 "AI 챗봇 전환" 신청이 보이지 않는다는 글이 있어(비공식), 챗봇 관리자센터에 직접 문의해야 합니다.
  • PoC에는 카카오 요청 형식을 받아 콜백으로 답하는 연결부가 없어서 새로 만들어야 합니다.

공식 문서 원문

"콜백 옵션을 설정할 경우 카카오 챗봇 플랫폼의 스킬의 처리시간 SLA(skill timeout: 5sec) 초과될 때에도 응답을 받아올 수 있습니다."카카오 비즈니스 가이드 · AI 챗봇 콜백 개발 가이드
"일정시간(callbackUrl valid time: 5min)동안 유효하며 1회에 한하여 사용할 수 있습니다."같은 가이드 (고객센터 도움말에는 1min으로 적혀 있음)
가능생성 시점 판단은 개발 필요

STEP 3. 노션 티켓 생성

되는 것

  • CS 요약, 단계, 우선순위, 카테고리, 접수 채널, 담당자, 요청자 연락처, 할당일, 완료일은 API로 씁니다.
  • CS 번호와 등록일시는 노션이 자동으로 채웁니다.
  • 이미 등록된 카드 템플릿을 적용해서 만들 수 있습니다.

조건 · 확인 안 된 것

  • 템플릿은 API로 만들 수 없습니다. 지금 보드에는 등록된 템플릿이 0개라, 노션 화면에서 먼저 만들어야 합니다.
  • 템플릿 적용은 백그라운드에서 진행되고, 본문 내용을 함께 보낼 수 없습니다.
  • "문의가 끝났다 / 명확해졌다"를 판단할 근거가 PoC에 없습니다. 질문 API(app/main.py:32)가 질문 한 줄만 받고, 대화나 사용자를 구분하지 않습니다.
  • 후보 신호: PoC가 이미 하는 "상담원 연결" 판정(app/pipeline.py:211), 사용자가 누르는 "상담직원 연결" 버튼

공식 문서 원문

"Notion assigns the number; you cannot set it in a page write."Notion API · Page property values (unique_id)
"The Notion app can be used to create and manage templates."Notion API · Creating pages from templates
"챗봇과 연결된 채널에서 1:1 채팅 혹은 상담톡 기능 연결 시, 사용자에게 '상담직원 연결' 혹은 '챗봇 전환' 버튼이 노출되어 대화 모드를 변경할 수 있습니다."카카오 비즈니스 고객센터 도움말
조건부

STEP 4. 크루 처리와 단계 변경 감지

되는 것

  • 크루가 단계를 바꾸면 노션이 우리 서버로 알림(웹훅)을 보냅니다.
  • 알림을 받은 서버가 할당일·완료일을 채우고, "완료"면 STEP 5를 시작합니다.
  • 알림마다 수정 주체가 사람인지 봇인지 표시돼서, 우리 서버가 한 수정은 걸러 낼 수 있습니다.

조건 · 확인 안 된 것

  • 공개 HTTPS 주소가 필요합니다. 지금처럼 로컬에서 띄운 서버로는 받을 수 없습니다.
  • 알림에는 무엇이 바뀌었는지 ID만 들어 있어서 값을 다시 조회해야 합니다.
  • 지연(보통 1분 이내, 최대 5분), 순서 뒤바뀜, 유실이 생길 수 있습니다. 주기적으로 상태를 맞춰 보는 조회가 필요합니다.
  • 우리 서버가 날짜를 채운 수정이 다시 알림으로 돌아오는지는 문서로 확인되지 않아, 실제로 시험해 봐야 합니다.

공식 문서 원문

"The events themselves do not contain the full content that changed."Notion API · Webhooks events delivery
"We aim for at-most-once event delivery." / "Events may arrive in a different order than they occurred."같은 문서
조건부

STEP 5. 처리 결과 통지

되는 것

  • 채널을 추가한 사용자에게는 STEP 1의 사용자 구분키로 챗봇이 먼저 메시지를 보낼 수 있습니다(Event API).
  • 채널을 추가하지 않은 사용자에게는 전화번호로 알림톡을 보낼 수 있습니다.

조건 · 확인 안 된 것

  • 방법별 조건은 아래 4절 표에 정리했습니다.
  • Event API의 광고 표시 예외("고객의 요청에 의해 발송하는 1회성 정보")에 CS 처리 결과 통지가 해당하는지는 확인되지 않았습니다.
  • 상담톡을 쓰는 경우, 상담 세션이 열리기 전에는 상담원이 먼저 말을 걸 수 없습니다.

공식 문서 원문

"Event API는 채널을 추가한 유저에게만 전송 가능하므로, 채널을 추가하지 않았거나 차단한 경우 전송은 실패합니다."카카오 비즈니스 가이드 · Event API
"상담 세션이 열리기 전까지는 상담원이 카카오톡 이용자에게 먼저 말을 걸 수는 없습니다."카카오 비즈니스 가이드 · 상담톡

(웹훅 보내기 동작)		 유료 요금제 "단계가 완료로 설정될 때"처럼 조건을 좁게 걸 수 있고, 속성 값이 함께 옵니다. 전송이 한 번 실패하면 자동화가 일시정지되고, 사람이 다시 켜야 합니다. 보내는 내용을 미리 볼 수 없습니다.

요청 수 제한: 비즈니스·엔터프라이즈 요금제 분당 600회, 그 외 분당 180회. 이 워크스페이스의 요금제는 API로 확인할 수 없어 아직 모릅니다.

5현재 상태 점검 (직접 확인)

노션 보드 "CS 처리 보드"

  • 요청자 연락처가 이메일 형식입니다. 카카오 사용자 구분키나 전화번호를 담을 속성이 없습니다.
  • 접수 채널 선택지(문의 폼, 이메일, 커뮤니티, 기타)에 카카오톡 채널이 없습니다. API로 추가할 수 있습니다.
  • 단계의 네 값이 모두 할 일 그룹에 있습니다. 진행중·완료 그룹으로의 재배치는 API로 가능하다고 문서에 나옵니다(미시험).
  • 등록된 카드 템플릿이 0개입니다.
  • 지금 연결된 노션 통합으로 이 보드를 읽고 쓸 수 있습니다.

CS 답변 PoC 기능 브랜치에서 구현

  • 상담 종료 → 노션 티켓: 채팅 화면의 "상담 종료" 버튼을 누르면 LLM이 대화를 요약·분류해 CS 처리 보드에 카드를 만듭니다. 챗봇 답변이 상담원 연결로 분류되면 버튼 없이 바로 만듭니다.
  • 대화 문맥 전달: 질문할 때 최근 6개 메시지를 함께 보냅니다. 자세한 내용은 6절에 있습니다.
  • 대화 기록은 브라우저에만 있어, 새로고침하면 사라집니다. 서버 세션은 아직 없습니다.
  • 맞는 위키 페이지가 없거나 확신이 낮으면 "상담원 연결"로 분류합니다. 이때 화면이 그때까지의 대화로 티켓을 바로 만들어 담당자에게 넘기고 상담을 끝냅니다.
  • 로컬 개발 서버로만 실행됩니다. 카카오·노션 요청을 받으려면 공개 HTTPS 배포가 필요합니다.
  • 문맥이 이어지자 챗봇이 "인증 코드를 발송하겠습니다"처럼 실제로 할 수 없는 조치를 약속하는 문제가 확인됐습니다. 답변 지침 보강이 필요합니다.

6대화 문맥 관리 방식

대화 문맥을 끝없이 유지할 수는 없습니다. 아래는 OpenAI, Anthropic, LangChain·LangGraph, LlamaIndex, Google Dialogflow CX, AWS Lex V2, Microsoft Copilot Studio 공식 문서에 나오는 방식입니다. 인용 문구는 원문에 그대로 있는지 대조했습니다.

서버 세션 저장 + 만료 대화별 상태를 서버에 저장하고, 일정 시간 요청이 없으면 끝냅니다. 기본값은 AWS Lex 5분, Dialogflow 30분이고, 최대는 둘 다 24시간입니다. 만료가 짧으면 고객이 처음부터 다시 말해야 하고, 길면 저장 부담이 커집니다. 미적용
브라우저에만 보관
명시적 초기화 대화 종료 시점에 맥락을 비웁니다. 확인한 공식 문서에 주제 전환을 자동으로 감지하는 기법은 없었습니다. 동작이 확실합니다. 초기화 시점은 직접 설계해야 합니다. 적용함
상담 종료 버튼으로 비움

실제 서비스라면 (조사 결과를 바탕으로 한 판단)

출처가 직접 언급한 조합은 "요약 + 최근 원문 유지", "이력 반영 질문 재작성 후 검색", "세션 만료 후 이전 상태 복원"입니다. 이 조합들이 실제 상담 챗봇에서 얼마나 널리 쓰이는지는 어느 출처에도 없습니다. 아래는 이를 이 서비스에 맞춰 본 판단입니다.

  • 세션을 서버에 저장합니다. 카카오 채널을 붙이면 챗봇 요청에 담기는 사용자 구분키를 세션 키로 씁니다. 지금의 브라우저 보관은 PoC용입니다.
  • 세션 만료를 둡니다. 대화가 일정 시간 멈추면 만료 처리합니다. 만료를 "티켓을 만드는 시점"과 묶으면, 상담 종료 버튼 없이도 자동으로 티켓이 생깁니다.
  • 지금 방식은 그대로 둡니다. 최근 N개 유지와 검색용 질문 재작성은 이미 적용돼 있습니다.
  • 긴 상담이 많아지면 요약 + 최근 원문 유지로 넓힙니다. 지금 단계에서는 필요 없습니다.
  • 개인정보를 걸러 냅니다. 상담 챗봇에 특화된 공식 지침은 찾지 못했습니다. Anthropic 문서에 저장 전 민감 정보를 걸러 내고, 오래 안 쓴 기억은 주기적으로 지우라는 일반 지침이 있습니다. 테스트 대화에서 고객이 휴대폰 번호를 채팅에 적은 사례가 실제로 있었습니다.

지금 코드에서 알아 둘 점 · 프롬프트 캐싱

  • 요청마다 똑같이 반복되는 앞부분은 캐싱으로 싸게 처리됩니다. OpenAI는 최대 95% 할인하며, 1,024 토큰 이상이어야 캐시됩니다. OpenAI 문서는 고정된 내용을 앞에 두라고 권합니다.
  • PoC는 답변 생성 입력에서 이전 대화를 위키 문서보다 앞에 넣습니다. 그래서 대화가 길어질수록 캐시가 덜 맞을 수 있습니다(문서 문구에서 추론).
  • 지금 답변 지침은 짧아서 캐시 최소 길이에 못 미칠 가능성이 큽니다(토큰 수는 재 보지 않음). 그래서 지금 당장은 순서를 바꿔도 차이가 없을 수 있습니다. 지침이 길어지면 다시 검토합니다.

7정해야 할 것

1

티켓을 만드는 시점

PoC가 "상담원 연결"로 분류했을 때, 사용자가 "상담직원 연결"을 눌렀을 때, 대화가 일정 시간 멈췄을 때 중 무엇을 기준으로 할지 정해야 합니다. 지금 PoC는 상담 종료 버튼을 누를 때와 상담원 연결로 분류됐을 때 만듭니다. 대화가 멈췄을 때를 추가하려면 아래 세션 만료와 함께 정해야 합니다.

2

처리 결과 통지 방식

Event API를 쓰면 채널을 추가한 사용자에게만 건당 15원으로 보낼 수 있습니다. 알림톡을 쓰면 모든 사용자에게 보낼 수 있지만 딜러사 계약, 템플릿 심사, 전화번호 수집이 필요합니다. 고르는 쪽에 따라 노션 보드에 저장할 값(사용자 구분키 또는 전화번호)도 정해집니다.

3

노션 요금제

유료 요금제면 단계 변경 감지에 데이터베이스 자동화를 쓸 수 있습니다. 무료 요금제면 연동 웹훅만 쓸 수 있습니다. 요금제는 API로 확인할 수 없어서 알려 주셔야 합니다.

4

카카오 쪽 사전 확인

챗봇 관리자센터에 콜백 사용에 신청·승인이 필요한지, 채널이 비즈니스 인증을 받았는지 확인해야 합니다. Event API를 쓰려면 비즈니스 인증이 필수입니다.

5

대화 세션 저장 위치와 만료 시간

대화를 서버에 몇 분 동안 보관하고, 만료되면 어떻게 할지 정해야 합니다. 예를 들어 만료 시 자동으로 티켓을 만들거나 그냥 버릴 수 있습니다. 참고 기준은 AWS Lex 기본 5분, Dialogflow 기본 30분이고, 최대는 둘 다 24시간입니다. 짧을수록 고객이 다시 설명해야 하는 일이 늘고, 길수록 저장 부담과 개인정보 보관 기간이 늘어납니다.

6

챗봇이 할 수 없는 조치를 약속하지 않게 하기

답변 지침에 "직접 처리할 수 없는 조치(코드 발송, 정보 변경)는 약속하지 말고 상담원 연결을 안내한다", "개인정보를 채팅에 적어 달라고 요청하지 않는다"를 넣을지 정해야 합니다. 넣으면 대화가 덜 매끄러워 보일 수 있지만, 고객에게 거짓 약속을 하지 않게 됩니다.

8출처와 신뢰도

모든 출처는 2026-10-18에 확인했습니다. 카카오 문서와 대화 문맥 관리 문서 인용은 원문과 대조했습니다. 노션 문서 인용은 웹 페이지를 요약해 가져오는 도구로 얻은 것이라 몇 단어 다를 수 있습니다. 설계에 확정 반영하기 전에 원문 대조가 필요합니다.
